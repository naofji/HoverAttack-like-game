# ミニマップのオーバーレイ 設計

2026-08-14〜16。テストプレイヤーからの指摘を起点に、ミニマップを
「一瞬だけ出る小さな図」から「R キーで開きっぱなしにできる、実際の地形の
半透明オーバーレイ」へ作り替えた一連の変更をまとめる。

**この文書は後追いで書いている。** 実装は commit `891dfc8`〜`f8a2f2a` に
分かれて入っており、途中の判断の理由がコミットメッセージにしか無い状態
だったため、続きを触る人のためにここへ集約した。

## 何を作ったか

| 変更 | 指摘・要望 |
|---|---|
| R キーを再度押すまで開いたままにする | 「移動すると消えるのではなく、R を再度押すまでオーバーレイした方がいい」（テストプレイヤー） |
| 実際の地形バッファから焼く | 「今のやり方だとどうしても実際の地形と異なる。実際の背景を縮小して、彩度と明度を落として半透明に」 |
| 大きさ・薄さの調整 | 1/3 → 1/2 → **0.4**（画面幅比）。「薄くなったのでサイズは大きくて大丈夫」 |
| 外枠を無くす | 白い枠が目立つ → グレー → 「外枠は無しでも良さそう」 |
| 四隅を移動して自機・クロスヘアを避ける | 「プレイヤーやクロスヘアをよける形で」 |
| 隅の切り替えをフェードでつなぐ | 「パッと変わるとうるさい」 |
| カーソルと反対側に置く | 「マウスカーソルがある側とは反対方向にあるのがいい」 |
| 母艦の方向矢印をミニマップより上の面へ | 「インディケーターが見づらくなる」→「いっそミニマップより上のプレーンに表示してしまえば位置の問題は解決する」 |
| その矢印を半透明に | 「インディケータ自体も半透明にしたらどうでしょう？」 |
| 自機が**近づいた**段階で避け始める | 「プレイヤーが近づいているにも関わらず位置が変わらない。今のままではプレイヤーがミニマップと重なってしまう」（2026-08-16） |
| マップの広さによらず表示サイズを一定に | 「マップの広さにかかわらずミニマップの大きさを一定に保つことはできますか？」（2026-08-16） |
| 可視領域を明るく示す | 「サイズを固定したため、全体マップがどれくらい広いのかが分かりにくくなった」（2026-08-16） |

## 地形は tile cache から焼く

`Map._generateMiniMap()` は、以前はタイルの配列を1マスずつ塗り直していた。
これだと**実際に描かれている地形とは別の絵**になり、破壊で地形が変わっても
追従しない。

現在は、地形描画の高速化のために持っている **`tileCacheCanvas`（実際に画面へ
出しているのと同じ絵）を1回の `drawImage` で縮小して焼く**。背景色
（`COLOR_CAVE_BG`）を先に塗ってから重ねるので、洞窟の空洞も塗り残しにならない。

トーンは `ctx.filter`（`saturate` / `brightness`）で落とす。`filter` が使えない
環境では合成モード（`globalCompositeOperation`）へフォールバックする。
**この2経路は同じ絵を出さなければならない**（背景色を塗る手順が片方に無く、
経路によって見た目が変わるバグを実際に出した。`05613b9`）。

焼き直しは**開いて描く直前に、必要なときだけ**行う。`invalidateTileRegion()`
（地形が壊れたときに呼ばれる既存の口）が `miniMapDirty` を立て、
`refreshMiniMap()` がそれを見て1回だけ焼く。閉じている間は焼かないので、
毎フレームのコストは増えない。

**`_initTileCache()` は `_generateMiniMap()` より先に呼ぶ必要がある**
（焼く元が無いと真っ黒になる）。この順序は `Map` のコンストラクタで担保している。

## 置き場所 — カーソルがいる側の反対側

`src/js/ui/minimapPlacement.js` の `pickStickyMiniMapCorner()`（純関数、
`node --test` で直接テストする）。

**画面の中心線で左右・上下を独立に見て、カーソルがいる側の反対側の隅を選ぶ。**
中心線の前後には不感帯（`MINIMAP_SIDE_HYSTERESIS` = 0.15。隅と隅の間隔に対する比。
1024×768 で横 ±87px / 縦 ±71px）を置き、カーソルが中央付近で揺れている間は
動かないようにする。

自機（ドッキング中は母艦）に**近づかれた**隅は避ける。裏返す順は **上下 → 左右 → 両方**。
カーソルとの左右関係のほうが体感で効くので、まず上下だけを裏返して左右を保つ。

### 自機側の余白 — 「近づいているのに動かない」（2026-08-16、実機指摘）

初版は**自機の当たり判定だけ余白ゼロ**だった（クロスヘアには
`MINIMAP_AVOID_PADDING` があった）。つまり自機が矩形へ**入るまで**動き出さない。
さらに隅の切り替えはフェードを挟むので、入ってから動き始めたのでは
**必ず一度は重なる**（`MINIMAP_FADE_SPEED` 0.08 ＝ 消えるまで約13フレーム）。

`pickStickyMiniMapCorner()` に `unitPadding` を足し、
`MINIMAP_AVOID_PADDING_UNIT`(64) を渡すようにした。64 の内訳は
**自機の半分(8px) ＋ フェード中に自機が動く距離(速度3で約38px) ＋ 余裕**。
`unitPadding` の**既定は 0**（＝従来の挙動）なので、他の呼び出しには影響しない。

**余白を足しても「逃げ場が無くなる」ことは起きない。** 実寸(1024×768)で確認済み:
余白を含めた四隅の判定領域は横も縦も重ならない（横 489.6 < 534.4、縦 344.8 < 483.2）
ので、1つの点が同時に2つ以上の隅を塞ぐことは幾何的に起こらない。
**表示サイズや余白を大きくするときは、この重なりが生じないか必ず確認すること。**

### 初版の欠陥 — 対角2隅しか使えなかった（2026-08-15、実機指摘）

**指摘**: 「右上にミニマップが来ることが1度もありませんでした。何か偏りが
起こる原因があるはずです。」

初版のルールは「**今いる隅**にカーソルが乗ったら動く。動き先は**カーソルから
最も遠い隅**」だった。これは構造的に対角2隅しか使えない:

- 動く条件が「カーソルが**今の隅**に乗ること」
- そのときカーソルは今の隅の上にいるのだから、最も遠い隅は**必ず対角**
- 結果 `topLeft → bottomRight → topLeft →…` の閉じたループになり、
  **右上と左下は理論上到達不能**

実際の画面サイズ（1024×768）で本物の関数を4000回走査したところ、占有は
`topLeft` と `bottomRight` のみ、遷移も両者の往復2種類だけだった。

**修正は「動く条件」と「動き先」を同じ1つの基準にまとめること。** 基準を
「今の隅」から「画面の中心線」に移したので、動き先はカーソルの位置だけで
決まり、4隅すべてが出る（同じ走査で右上 0回 → 884回、占有はほぼ均等）。
往復しない性質は、不感帯とフェードが引き継いでいる。

**教訓**: この偏りは一度「問題なし」と誤って報告している。ロジックを書き写した
簡略モデルで走査したためで、**本物の関数を import して実際の定数で回す**必要が
あった。占有率だけでなく**遷移の集合**を出すと、閉じたループがすぐ分かる。

### 回帰テスト

`tests/minimap-placement-sticky.test.js` に**「カーソルを画面じゅうに格子状に
動かすと4隅すべてが選ばれる」**がある。乱数は使わず格子で走査する（不安定な
テストにしないため）。初版の実装ではこれが落ちる。

## 隅の切り替えはフェードでつなぐ

`src/js/ui/minimapTransition.js` の `advanceMiniMapTransition(state, desired, speed)`。
今の隅でフェードアウト → 新しい隅でフェードイン、を `MINIMAP_FADE_SPEED`(0.08) で
進める状態機械。**地形だけでなく、上に打つ点（自機・敵・母艦）にも同じ
`fade` を掛ける**（点だけ即座に移動して見えるバグを出した。`615fc2d`）。

## 表示サイズはマップの広さによらず一定（2026-08-16）

焼く解像度は `cols × miniMapScale(2)` なので**マップの広さに比例する**（最小の
150×75 タイルで 300×150px、最大の 300×150 タイルで 600×300px）。以前はこれを
「画面幅の `MINIMAP_MAX_WIDTH_RATIO` を**上限**として縮小、小さければ等倍」と
していたため、**面が進んでマップが広くなるほどミニマップも大きくなっていた**。

現在は上限ではなく**目標**として扱い、常に画面幅の 0.4 倍に合わせる
（1024×768 なら 409.6×204.8）。縦が HUD 帯の間に収まらないマップだけ高さ側で
頭打ちにする。アスペクト比は常に保つ。

**小さいマップは拡大されることになる**（元絵 300px → 409.6px、約1.37倍）。
ミニマップは元々彩度と明度を落として沈めた絵なので、多少の甘さは許容する。
気になるなら `Map._generateMiniMap()` の `miniMapScale` を上げて焼く解像度自体を
増やす手があるが、**この値は点や可視領域の座標計算が前提にしている**ので
影響範囲は広い。

## 可視領域のハイライト（2026-08-16）

サイズを固定した副作用として「全体マップがどれくらい広いのか分かりにくい」と
指摘された。**可視領域（カメラの矩形）は常に 64×48 タイルで固定**なので、
それがミニマップに占める割合が**そのまま縮尺の手がかりになる**:

| マップ | 可視領域の見た目 | ミニマップに占める割合 |
|---|---|---|
| 最小（150×75 タイル） | 175×131px | 43% × 64% |
| 最大（300×150 タイル） | 87×66px | 21% × 32% |

面積で4倍の差があるので、面をまたぐと広さの違いが分かる。**サイズ固定と
縮尺の手がかりは競合しない**（固定したからこそ、この割合が縮尺を意味する）。

### なぜ「外を暗く」ではなく「中を明るく」か

「外側を暗くする（境界がそのまま枠になる）」案を提案したが、**ユーザーが却下**した:
ミニマップは既に彩度・明度を落として沈めてあり、**これ以上暗い部分を作ると
マップとして読めなくなる**ため。

### なぜ「白を重ねる」のか（不透明度を上げるのではなく）

ミニマップは**ライブのゲーム画面の上に半透明で乗っている**。そのため
「地形をもう一度重ねて不透明度を上げる」方式だと、**背後に何が映っているかで
コントラストが変わり**、狙った差が出る保証がない。白（`COLOR_MINIMAP_VIEWPORT`）を
`MINIMAP_VIEWPORT_HIGHLIGHT`(0.15) で重ねるのは背後に依存せず、必ず明度が上がる。

### 描画順と濃さの規則

- **地形 → 可視領域のハイライト → 点**。点を必ず後にするのは、ミニマップを開ける
  一番の目的が「**画面に映っていない**敵がどこにいるか」だから。赤い点が白に
  埋もれてはいけない
- ハイライトの濃さは開閉フェードと隅の切り替えフェードに追随させるが、
  **`MINIMAP_ALPHA` は掛けない**（あれは地形を背景に沈めるための値で、
  ハイライトは沈める対象ではない）
- 縮尺は点と同じ `viewScale`（`miniMapScale × 縮小率`）を**共有する**。
  別々に持つと点とハイライトがずれる
- カメラが範囲外へ出たとき（画面揺れなど）に白がミニマップの外へ漏れないよう
  クランプする。通常のカメラは `[0, マップ幅 - 画面幅]` にクランプされるので、
  この経路は防御的なもの

## 母艦の方向矢印は上の面に描く

以前は矢印もミニマップが避ける対象の1つだった（避ける点が3つになり、置ける隅が
さらに減っていた）。現在は **`HUD.drawCarrierArrow(ctx)` を `_drawOverlays()` の
**後**に呼んでミニマップより上の面に描く**ので、重なっても矢印が前に出る。
矢印自体も `CARRIER_ARROW_ALPHA`(0.7) で半透明にして、下のミニマップを透かす。

`main.js` の描画順がこの仕様の本体なので、順番を入れ替えないこと。

## 定数（すべて `src/js/utils/Constants.js`）

| 定数 | 既定値 | 根拠 |
|---|---|---|
| `MINIMAP_MAX_WIDTH_RATIO` | 0.4 | 画面幅に対する幅。**上限ではなく目標**（マップの広さによらず一定サイズにするため）。1/3 → 1/2 と試して 0.4 に落ち着いた。1/2 は左右の候補が完全に重なるので却下 |
| `MINIMAP_ALPHA` | 0.6 | オーバーレイの薄さ（地形のみ。点とハイライトには掛けない）。0.85 → 0.55 → 0.6 |
| `MINIMAP_VIEWPORT_HIGHLIGHT` | 0.15 | 可視領域に重ねる白の濃さ。テストで 0.25 を上限として縛っている（地形を白く潰さないため） |
| `COLOR_MINIMAP_VIEWPORT` | `#FFFFFF` | 可視領域のハイライト色 |
| `MINIMAP_SATURATION` | 0.55 | 彩度を落として背景に沈める |
| `MINIMAP_BRIGHTNESS` | 0.65 | 明度も落とす。前景の点を目立たせるため |
| `MINIMAP_MARGIN` | 16 | 画面端／HUD帯からの余白 |
| `MINIMAP_AVOID_PADDING` | 48 | クロスヘアが「近づいたら」避け始める余白。実際に重なってからでは遅い |
| `MINIMAP_AVOID_PADDING_UNIT` | 64 | 自機／母艦側の余白。クロスヘアより大きいのは、隅の切り替えがフェードを挟むぶん早く動き始める必要があるため |
| `MINIMAP_SIDE_HYSTERESIS` | 0.15 | 中心線の不感帯。大きいほど動きにくい。0.3 まで上げると「反対側へ振っても付いてこない」領域が広くなりすぎた |
| `MINIMAP_FADE_SPEED` | 0.08 | 隅の切り替えのフェード速度 |
| `CARRIER_ARROW_ALPHA` | 0.7 | 母艦方向矢印の不透明度 |

## 実機で確認してもらうこと

- 4隅すべてに出るようになったか（特に**右上**）
- 中心線の不感帯が狭すぎ／広すぎないか（`MINIMAP_SIDE_HYSTERESIS`）
- 地形が壊れたあとミニマップが追従しているか（`invalidateTileRegion` → `miniMapDirty`）
- 大きさ 0.4・薄さ 0.6 が、遊びの邪魔にならず読める範囲か
- 自機が近づいたときに、重なる**前に**隅が切り替わるか（`MINIMAP_AVOID_PADDING_UNIT`）
- 小さいマップ（1面など）で拡大された地形が甘くなりすぎていないか
- 可視領域のハイライトが読めるか（`MINIMAP_VIEWPORT_HIGHLIGHT`。**薄すぎる方に
  外している可能性が高い**と見ている。効きが弱ければ 0.20〜0.25 へ）

2026-08-16 時点で、上記のうち**可視領域のハイライトと自機の回避は実機で
「いい感じ」と確認済み**。
