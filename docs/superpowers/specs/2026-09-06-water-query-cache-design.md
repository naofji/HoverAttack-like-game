# 水の問い合わせ層のキャッシュ化と滝判定の修正（案A） 設計書

日付: 2026-09-06

## 背景と課題

4面（地底湖）で「重い」「水の見た目が変」という2つの指摘があった。調べたところ、
**どちらも同じ1箇所** — 「このセルは水か・水面か・滝か」を毎回ゼロから調べ直している
問い合わせ層 — が原因だった。

### 課題1: 問い合わせが毎フレーム重い（実測 22.4µs/回）

依存の連鎖がこうなっている。

```
isWaterAtPixel / isWaterfallAtPixel
  └ isWaterSurface          … isWaterfallCell を2回呼ぶ
      └ isWaterfallCell     … 直下へ solid まで走査              O(rows)
  └ getSurfaceY
      └ getWaterSurfaceSegment … 左右へ走査し、各列で上の連鎖を再実行  O(cols × rows)
```

幅298タイルの水面で実測（本物の `Map.prototype` を使用）:

```
isWaterAtPixel     : 22.4 us/call
isWaterfallAtPixel : 21.4 us/call
```

これを毎フレーム呼ぶ場所:

| 呼び出し元 | 回数 |
|---|---|
| `motionFor()` — Player / Carrier / Bullet / Missile / Grenade / PickupItem / EnemyTank / EnemyAttacker / EnemyHomingMissile | エンティティごとに1回（滝判定→水判定で約40µs） |
| `StageEnvironment._trackWaterCrossings()` | 全エンティティ＋全弾＋破片に1回ずつ |
| `CombatActions._calcGrenadeTrajectory()` | **`GRENADE_LIFETIME=90` 回のループの中**。長押し中は毎フレーム 90×40µs ≒ 3.6ms |
| `beamPath.stepBeam()` | 反射ビーム1本あたり2〜5回 |

16.6ms の予算に対し、エンティティ100体で数ms〜十数ms。しかも**コストは水面セグメントの
幅に比例する**ので、水源からの流入で水域が広がるほど重くなる。
（memory の「描画は予算の 8.4%」はこの水流実装より前の値なので当てにならない。）

答えは水が動かない限り変わらないのに、毎回調べ直しているのが無駄。

### 課題2: 湖底を爆破すると湖を貫く縦縞が出る

`Map.js:1319-1333` の滝判定が「**自分より下のどこかに空気がある**」を条件にしている。

```js
let downR = r + 1;
while (downR < this.rows && !this.isSolid(downR, c)) {
    if (!checkWater(downR, c)) { hitsAir = true; break; }
    downR++;
}
if (hitsAir) return true;
```

湖底に穴が開くと、その列の水が水面まで全部この条件に当たり、滝として 8px の細帯で
描かれる。実際に走らせた結果（`|` が滝と判定されたセル）:

```
■ 爆破直後（まだ水は1ドットも動いていない。全セル mass=8）
#~~~~~~|~~~~~~~#      ← 水面が縦縞で分断される
#wwwwww|wwwwwww#
#wwwwww|wwwwwww#
#wwwwww|wwwwwww#
#wwwwww|wwwwwww#
#wwwwww|wwwwwww#
#######.########      ← ここのブロックを壊しただけ
```

穴が埋まるにつれ空気の位置が下がるので、縦縞が下から順に消える＝「波打って水面へ
移動していく」ように見える。さらに滝セルは `isWaterSurface` が false なので、
**水面の線がそこで途切れてセグメントが2つに割れ、左右で平均水位が変わる**
（上図の `~~~~~~|~~~~~~~`）。これが水面の揺れの正体。

**水量の減少は引き金ではない。** 水が動く前のフレームで既に発生している。

## 方針

`water[]`（水量）はそのまま残し、**そこから導かれる要約を2本の配列にキャッシュする**。
シミュレーション（`waterSimulation.js` の流れの計算）には一切触らない。

### 1. データ構造

`Map` に `water[]` と並べて2本持つ。どちらも `rows * cols`。

| 配列 | 型 | 内容 |
|---|---|---|
| `waterKind` | `Uint8Array` | `0`=水なし / `1`=水中 / `2`=水面 / `3`=滝（落下中） |
| `waterSurfaceY` | `Int16Array` | 水面セルの液面 Y（px、四捨五入）。セグメント平均を全メンバに書き込む。水面以外は `-1` |

`waterSurface`（現行の Int16Array、水面の「行」を持つ）は**廃止**し、`waterSurfaceY` が
役割を引き継ぐ。現行 `waterSurface` は生成時に書くだけで production では一度も読まれて
いない（読むのは `waterSurfaceRow()` の再計算のほう）。

### 2. 滝の判定を局所ルールに置き換える

現行の下向き走査をやめ、**自分も直下も満水未満で、かつ直下が非固体なら滝**にする。
O(1) になり、`isWaterfallCell` の O(rows) 走査が消える。

```js
water[k] >= MIN_WATER_MASS &&
water[k] < MAX_WATER_MASS &&
!isSolid(r + 1, c) &&
water[k + cols] < MAX_WATER_MASS
```

判定の意味づけは「**満ちたセルは落ち着いた水であり、満ちたセルはその上の水を支える。
どちらも満ちていない縦の並びだけが、落下の途中の水柱**」。

#### 候補の比較（実測）

4つのルールを3つの場面で走らせ、「帯⇄満水」の往復回数（＝画面のちらつきの量）を数えた。

| ルール | 湖底の爆破（120f） | 既存テスト `water-springs.test.js:399` | 天井からの滝（300f） |
|---|---|---|---|
| 現行「下のどこかに空気」 | 49（**縦縞バグ**） | 通過 | — |
| A「直下が空気（mass 0）」 | 11 | **失敗** | 0 |
| B「直下が満水未満」 | 865 | 通過 | 0 |
| **C「自分も直下も満水未満」** | **0** | **通過** | **0** |

- **A** は湖の縞は消えるが、宙に浮いた mass=4 の水柱（既存テストの状況）を「水たまり」と
  判定してしまい、落下中の水が 16×16 のタイルで塗られる
- **B** はレベリングの途中で mass が一時的に 7 になった瞬間に上のセルが滝になるため、
  湖の内部に縞が湧いて激しく点滅した（865回）
- **C** は湖の中が全セル mass=8 なので絶対に滝にならず、往復回数が 0 になった。
  既存テストの期待とも一致する

**C を採用する。**

縦穴を落ちる滝の場面では A・B・C の結果が完全に一致し、往復回数はどれも 0 だった
（点滅の心配は滝そのものにはない）。

### 3. 更新の仕掛け

既にある `onWaterChanged(cells)` に相乗りする。新しい仕掛けは増やさない。

1. `onWaterChanged(cells)` で、変化したセルの**列**を `dirtyWaterCols`（Set）に積む
2. `Map.update()` の末尾で、dirty な列だけを作り直す
   - **列を下から上へ1回走査**して `waterKind` を決める（滝判定が O(1) なので走査は列あたり1回）
   - そこで見つかった水面セルについて、行セグメントを左右に伸ばして平均 Y を求め、
     セグメント全員の `waterSurfaceY` に書き込む。処理済みセグメントは再訪しない
3. `dirtyWaterCols` を空にする

コストは「変化した列の数 × rows」＋「その中の水面セグメントの幅」。水が落ち着けばゼロ。

`_generateWater()` の直後に全列を dirty にして1回作り直し、初期状態を揃える。

#### 「水が動き出すと重くなるのでは」の実測

実寸（300×150）のマップに幅200タイル・深さ8タイルの湖を作り、湖底を爆破してから
水が止まるまで600フレームぶん、本物の `stepWaterSimulation` が返す `changedCells` から
dirty 列を求めて再構築の時間を測った。

| | 中央値 | 95% | 最大 |
|---|---|---|---|
| dirty になる列数 | 42 | 50 | 53 |
| 走査するセル数 | 6,583 | 7,741 | 8,198 |
| **再構築の時間** | **16.5µs** | **23.3µs** | 361µs（初回フレームの JIT ウォームアップ。2フレーム目以降は 30µs 未満） |

理論上の最悪ケース（全300列を1フレームで作り直す＝45,200セル走査）でも **235.7µs**。
16.6ms の予算の 1.4% で天井が押さえられている。

思ったより増えない理由は2つ:

1. `stepWaterSimulation` は**実際に mass が変わったセルしか `changedCells` に入れない**。
   落ち着いた水たまりは横方向レベリングの対象になっても値が変わらず dirty にならない。
   湖の幅が200タイルでも dirty 列は最大53だった
2. **落下が律速**（`WATER_MAX_FALL_FLOW=2` × `WATER_FALL_INTERVAL=4` で1タイル16フレーム）
   なので、水が一気に広がる状況そのものが作りにくい。幅200の乾いた盆地へ流し込む条件でも
   dirty 列は最大39・9.5µs だった

費用の性質が逆になる点が本質:

| | 現行 | キャッシュ後 |
|---|---|---|
| 水が止まっている | 4,480µs/frame | **0µs** |
| 水が動いている | 4,480µs/frame | 約 17µs |
| エンティティが増える | 比例して増える | **増えない** |
| 水域が広がる | 比例して増える | **増えない** |

4面は水源からの流入で水域が広がっていく面なので、「後半ほど重くなる」現在の性質が
消えるのが実質的な効果。

### 4. 問い合わせ側

全部 O(1) の配列参照になる。**引数と戻り値は変えない**（呼び出し側は無修正）。

| メソッド | 実装 |
|---|---|
| `isWaterSurface(r,c)` | `waterKind[k] === 2` |
| `isWaterfallCell(r,c)` | `waterKind[k] === 3` |
| `getSurfaceY(r,c)` | `waterKind[k] === 2 ? waterSurfaceY[k] : r * TILE_SIZE` |
| `isWaterAtPixel(x,y)` | `waterKind` と `waterSurfaceY` の組み合わせのみ |
| `isWaterfallAtPixel(x,y)` | 同上 |
| `getWaterSurfaceSegment(r,c)` | **削除**（描画側の `water.js` が使っているので、そちらも `waterSurfaceY` を直に読む形に変える） |

`waterSurfaceRow(r,c)`（水面の「行」を返す）は残す。`StageEnvironment._trackWaterCrossings`
のしぶきと `EnemyDrone` の着水停止が使っており、上向きに辿るだけで滝判定を含まないため
今回のボトルネックではない。ただし `waterKind` があれば O(1) で答えられるので、
ついでに配列参照に置き換える。

### 5. 死にコードの掃除

- `fillDestroyedCells()`（`waterPools.js:76`）と `tests/water-flood.test.js` — production から
  呼ばれていない（`500bd20` で撤廃済み）。テストだけが import している
- `map.waterSurface`（Int16Array）— `waterSurfaceY` が引き継ぐ
- `waterSimulation.js:216` の「余剰を上の行へ持ち上げる」枝 — `water[]` は1セル
  `MAX_WATER_MASS` が上限なので `sumMass > capacity` になり得ず、**到達不能**

## テスト

**現行の遅い実装を参照実装としてテストに残し、キャッシュと突き合わせる。**
`tests/helpers/water-reference.js` に現行の `isWaterSurface` / `getSurfaceY` /
`getWaterSurfaceSegment` をそのまま写し（滝判定だけは新ルールC）、

- ランダムな地形と水量の組み合わせを多数生成し、全セルで参照実装とキャッシュが一致することを確認
- 水を動かした後（`stepWaterSimulation` を回した後）にも一致することを確認
- 湖底を爆破したケースで、湖の内部に `waterKind === 3`（滝）が現れないことを縛る（課題2の回帰テスト）

**mutation check**: 滝判定を現行の下向き走査に戻すと、爆破の回帰テストが
赤くなることを実際に確認する（memory「壊して落ちることを確かめる」）。

パフォーマンスは `tools/` にベンチを置かず、**テストで「dirty でないフレームは
`waterKind` を1バイトも書き換えない」を縛る**（呼び出し回数を数える）。実時間の
測定は環境差で不安定なので入れない。

## 実機で見ていただくこと

ハードリロード（Cmd+Shift+R）が必要。`index.html` が `main.js?v=1.0` でキャッシュを
効かせているため。

1. **軽くなったか** — 4面で敵が多い場面、特に**グレネードを長押しして軌道を出しながら**
   水辺で動いたときのカクつき
2. **縦縞が消えたか** — 湖底のブロックをグレネードで壊したとき。湖を貫く縦の筋と、
   水面の線が途切れて揺れる現象が出ないこと
3. **滝の見た目が変わっていないか** — 天井の水源から落ちる滝は、変更前と同じに見えるはず

調整用の定数は今回追加しない（判定ルールの変更のみ）。

## 今回やらないこと（次の段へ）

- **滝の太さを水量に比例させる**（指摘4）。当たり判定も帯の幅に合わせる必要がある
- **横方向の拡散の調整弁**（指摘2）。水面が続く区間の瞬間レベリングはそのままでよいが、
  水面が途切れた先へ進む速度に上限をかける
- **滝が点線に見える問題**（今回の調査で判明）。水源が 2 mass / 15フレーム 湧き、
  落下が 1タイル / 4フレーム なので、落ちる水の塊が **3.75タイルおき**に離れて並ぶ。
  実測した列の分類:

  ```
  frame  60  |...|...|..|....
  frame  90  .|..|...|...|...
  ```

  滝が連続した流れではなく、飛び飛びの水滴の列になっている。`WATER_SPRING_INTERVAL`
  と `WATER_MAX_FALL_FLOW` / `WATER_FALL_INTERVAL` の比を見直すか、描画側で補間する
  必要がある。指摘4（太さ）と同じ段でまとめて扱うのがよい
- **水源が止まらない件**（指摘1）は「マップがゆっくり水没してよい」との判断で対応しない。
  ただし `Map.js:1386-1389` の2つの停止ガードは**どちらも構造的に成立しない死んだ条件**
  なので（`sp.r` は不変、`sp.r-1` は必ず岩でその `water[]` は常に 0）、
  「意図的に止めていない」ことをコメントで明記する
