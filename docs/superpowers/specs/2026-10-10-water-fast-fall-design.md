# 水を速く落とす（候補B）＋ 滝の判定を流れの記録から作る 設計書

日付: 2026-10-10
ブランチ: `feat/water-fast-fall`（main d4a853c から。`src/js/main.js` の `debugStartMission` を巻き込まないこと）

## 目的

ユーザーの実機スクリーンショット（4面）で、水の塊が階段状の岩を下りる途中に
- 空中に浮いた満水の四角（真下が空洞）
- 棚の上に立つ垂直な水の壁
が出ていた。「保留していた B プランを採用し、滝の描き方も一緒に作り直す」。

### 原因

落下は 4フレームに1回・最大2（`WATER_FALL_INTERVAL` / `WATER_MAX_FALL_FLOW`）、横の流れは
毎フレーム最大4（`WATER_MAX_SPREAD_FLOW`）。落下が横の 1/8 しかないので、
- 落ちきる前に横へ広がって宙に張り出す
- 出口が落下中の1マスに絞られると、塊がそこから 0.5/フレームでしか抜けず段に居座る

合成の階段地形（スクリーンショットをタイルに起こしたもの）に塊を置いて放すと、
浮いた満水セル×フレーム 2927、階段の水が抜けきるまで約500フレーム。落下を毎フレームにすると
388・約100フレーム。

### B を保留していた理由（そのまま残っている）

湧き水は 4フレームに1回・水量1（`WATER_SPRING_INTERVAL` / `WATER_SPRING_MASS`）。落下が
4フレームに1回だと水量1の粒が 4フレームで1マス進むので、細い滝はどのセルにも常に水がある。
落下を毎フレームにすると粒は1マス/フレームで進み、**粒と粒のあいだが3マス空く**。
滝の判定（`isFallingCell`）はセルの中身だけを見るので、滝が点線になり、点滅する。

実物の4面（`tools/measure-water.mjs`、6シード×2400フレーム、150フレームおきに撃ち抜き）:

| 落下 | 浮いた満水の四角（延べ） | 滝の点滅（滝⇄滝以外の入れ替わり延べ） |
|---|---|---|
| 現状（4フレームに1回・2） | 682 | 43,995 |
| 毎フレーム・2 | 206 | 820,474 |
| 毎フレーム・4 | 208 | 820,392 |
| 毎フレーム・8 | 171 | 820,832 |

効くのは落下の**間隔**で、1回の量はほとんど関係ない。

### ユーザーの判断（2026-10-10）

- 湧き水の量は**今のまま**（4フレームに1回・水量1）。毎フレーム湧かせれば中身だけで滝が
  つながるが、湖が4倍速く満ちて面のバランスが変わる
- 案A「流れの記録を滝の判定そのものに入れる」を採用。案B「描画だけで点線を埋める」は、
  判定が点滅したままで、滝の押し流し・着水の波紋がちらつき、「1つの値は1か所で決める」
  （memory: one-level-one-definition）に反するので採らない

## 設計

### 1. 物理: 落下を毎フレームに、水圧は今の速さのまま

- `WATER_FALL_INTERVAL` 4 → **1**。定数は調整のつまみとして残す（1 なら `doFall` は毎フレーム真）
- `WATER_MAX_FALL_FLOW` は **2 のまま**（2・4・8 で差が無かった。変える理由が無い）
- **水圧を落下から切り離す。** いまフェーズ3（`stepWaterPressure`）は `doTransfer: doFall` で
  落下と同じフレームにだけ運ぶ。間隔を1にすると水圧が4倍速くなり、ユーザーが実機で
  「いい感じ」と確認した速さ（`WATER_PRESSURE_GAIN` など）が崩れる。
  新しい定数 `WATER_PRESSURE_INTERVAL = 4` を足し、`stepWaterSimulation` に `doPressure` 引数を
  足して `Map.update` が専用のタイマーで渡す。省略時は `doFall` と同じ（既存のテストの呼び方が通る）
- 湧き水は変えない。`WATER_SPRING_INTERVAL` のコメント（「落下の間隔と同じにする。長いと滝が
  途切れる」）は前提が変わるので書き直す — つながりは流れの記録が受け持つ

### 2. 流れの記録（新規 `src/js/world/waterStream.js`、純関数）

「細い流れがついさっきここを落ちた」を、セルごとに残りフレーム数で持つ。

- 配列 `hold: Uint8Array`（rows×cols）と、0 でないセルの一覧 `live: Set<number>`。持ち主は `Map`
- **書くのはシミュレーションの落下（フェーズ1）だけ。** 1回に落ちた量が
  `WATER_STREAM_MAX_FLOW`（= 1）以下のとき、落ちた元と落ちた先の両方に
  `WATER_STREAM_HOLD_FRAMES`（= 4）を書く
  - 量1に絞る理由: 大きな塊は2ずつ落ちるので、塊の通り道に滝の尾が残らない。
    試作で量1に絞っても点滅は 2,774 → 2,770 と変わらなかった（細い流れはどれも量1）
  - 4 にする理由: 湧き水の粒は4フレームおきに来るので、次の粒が通るまで記録が残る長さ。
    試作で 4・5・6 の点滅は 2,774・2,778・2,780 で差が無い。記録が長く残るほど流れが止んだ後の
    滝も長く残るので、差の無い中で最短の 4 を取る
- 毎フレーム、シミュレーションの前に `live` を1減らし、0 になったセルを返す。
  **`Map` はそのセルを `onWaterChanged` に渡して種別キャッシュに知らせる**
  （水量が変わらなくても種別が変わるので。memory: lazy-cache-every-writer-notifies）
- 乱数を使わない。週次の決定性は保たれる（マップ生成では水を流していない）
- 撃ち抜きで岩になったセル・マップの作り直しでの扱い: 岩のセルは判定側で除く（下記）。
  `Map` を作り直すときは配列ごと作り直す

### 3. 判定: `isFallingCell` に記録を足す（定義は1か所のまま）

```
滝 = 満水でない
   かつ 真下が水を支えない（supportsWater）
   かつ（水がある  または  流れの記録が残っている）
   かつ 岩でない
```

- `isFallingCell(water, rows, cols, isSolid, r, c, hold)`。`hold` を省略したら今までどおり
  （中身だけ）。`classifyWaterColumn` → `rebuildWaterCache` へ同じく省略可能な引数で通す
- `classifyWaterColumn` は今「水量0なら水なし」を先に決めているので、記録のある空のセルを
  滝として拾うよう順番を変える
- **読み手の側は変えない。** 種別を読むのは、滝の帯の描画（`waterfallRuns.js`）、着水の波紋
  （`waterfallLandingCols`）、押し流し（`StageEnvironment` の `isWaterfallAtPixel`）、
  水中の判定（`isWaterAtPixel`。滝なら水）、泡のマス（真上が滝なら泡にしない）、
  塗りの上端（滝は塗らない）、液面（真上が滝なら液面）。
  記録のある空のセルが「滝＝水」になるのは、いま（落下が4フレームに1回）細い滝のどのセルにも
  水がある状態と同じ扱いに戻るだけ

試作の結果（4面・6シード×2400フレーム、量1に絞り、保持4）: 点滅 **2,770**（現状 43,995）、
浮いた満水の四角 206（現状 682）、水量の保存違反 0。作り直しの95%点 208→254µs、
`map.update` の95%点 217〜233→265µs（測るたびに数十µs揺れる。どちらも予算の範囲。
memory: hoverattack-view-culling）。

### 4. 描画の整理（`waterfallRuns.js`）

セルが一瞬空になる前提で足した継ぎはぎが3つある。

1. 下へ辿るとき、1マスの空き（水量1の塊の継ぎ目）を越えて1本にする
2. 上端が空中なら1マス遡って判定し直す（水源の口・落ち際が一瞬空になるため）
3. `addDrainSpills`: 床の水が流れ込む落ち口には、その瞬間セルが空でも滝を描く

**1つずつ外して測り、要らなくなったものだけ消す。** 外して描いた滝が増減・点滅しなければ
消し、コメントに測った数字を残す。消せなかったものは、なぜ要るかをコメントで書き直す。

測るため `tools/measure-water.mjs` に指標を足す:
- `runFlicker`: マップ全体の `collectWaterfallRuns` が描く帯が覆うセルの、1フレームでの
  入れ替わりの延べ数（種別ではなく、実際に描く帯の点滅）
- `floatingHeads` の数え方を直す: 今は「真上の水量が0」で数えるので、記録で空のセルが滝に
  なると意味を失う（試作で 1,283,181 に跳ねた）。「真上が岩でも水でも滝でもない」で数える

見た目は `tools/render-water-scene.mjs` で前後を PNG に書き出して見比べる（連続する
フレームを数枚。1枚は良いフレームを写すだけなので、点滅は数で見る。
memory: visual-check-render-and-count）。

### 5. テスト

新しく縛るもの（どれも、わざと壊して赤くなることを確かめる）:
- 落下が毎フレーム起きる（`WATER_FALL_INTERVAL` が1のとき、空中の水が1フレームで落ちる）
- **湧き水の細い滝が、毎フレーム口から着水点まで滝として1本につながる**（実物の `Map` で
  N フレーム回し、区間の中に滝でないセルが無い）。壊し方: 保持を 1 にする／記録を書かない
- **大きな塊の通り道に滝の尾が残らない**（塊を落とし切った後、記録のある空のセルが無い・
  滝のセルが無い）。壊し方: 量の絞りを外す
- **水圧の速さが変わらない**（`tests/water-pressure.test.js` の時間の計測を
  `WATER_PRESSURE_INTERVAL` で回し、同じフレーム数で同じ量が動く）。壊し方: `doPressure` を
  `doFall` に戻す
- 記録が切れて種別が変わるとき、キャッシュが全列作り直しと一致する。壊し方: 期限切れの
  `onWaterChanged` を外す
- `waterStream.js` の単体（書く条件・減り方・期限切れの一覧）

書き直すもの:
- `tests/water-springs.test.js` の「湧き出る周期は落下の間隔と同じ」（464行あたり）は前提が
  変わるので、「滝として1本につながる」へ置き換える
- `WATER_FALL_INTERVAL` で回している `water-pressure` / `water-active-invariant` /
  `water-springs` は、落下と水圧の間隔を本番と同じに回す形にする

既知の失敗: `tests/enemy-spawn-determinism.test.js` の面7の戦車の湧き位置の重複は main でも
落ちている（この作業とは無関係。触らない）。

## 遊びの変化（ユーザーに伝える）

- 穴を開けた湖が約4倍速く抜ける（出口1マスの落下が 0.5 → 2/フレーム）
- 水の塊が階段や棚で居座らず、滝として落ちていく
- 水圧（連通管）の速さ・湧き水の量は変わらない

## 実機で見てもらう点と調整の定数

| 見る点 | 定数 |
|---|---|
| 塊の落ちる速さ | `WATER_MAX_FALL_FLOW`（1回の量）・`WATER_FALL_INTERVAL` |
| 細い滝が途切れない・塊の後に尾が残らない | `WATER_STREAM_HOLD_FRAMES`・`WATER_STREAM_MAX_FLOW` |
| 連通管の速さが前と同じ | `WATER_PRESSURE_INTERVAL` |

## やらないこと

- 湧き水の量の変更（ユーザー判断）
- 横の流れの左右非対称（`waterSimulation.js` ケースAのコメント。点滅を嫌って意図的に残している）
- 階段の水面が `sameBody` で1つの平均にまとまる既存の問題（別の設計が要る。memory: hoverattack-phase-plan）

## 結果（実装後の実測、2026-10-10）

`node tools/measure-water.mjs`（4面・6シード×2400フレーム、150フレームおきに撃ち抜き）の total:

| 指標 | 変更前（Task 1） | 落下を毎フレーム＋流れの記録（Task 4） | 描画の整理後（Task 5） |
|---|---|---|---|
| 浮いた満水の四角 `floatingFull` | 682 | 207 | 207 |
| 滝の種別の点滅 `flicker` | 43,995 | 2,966 | 2,966 |
| 描いた滝の帯の点滅 `runFlicker` | 16,909 | 4,407 | 4,162 |
| 宙に浮いた滝の始まり `floatingHeads`（このブランチで数え方を直した後の定義） | 215,591 | 219,412 | 219,412 |
| 水量の保存違反 `massViolations` | 0 | 0 | 0 |
| `map.update` の95%点（µs） | 247 | 279 | 310 |
| キャッシュ作り直しの95%点（µs） | 224 | 330 | 361 |

（時間は測るたびに数十µs揺れる。1フレーム 16.7ms に対して十分小さい）

`waterfallRuns.js` の継ぎはぎ3つ:
- 列の途中の1セルの空きを越える処理 — **外した**（runFlicker 4,407 のまま）
- 上端を1セル遡る処理 — **外した**（runFlicker 4,407 → 4,162）
- `addDrainSpills`（床の水の行き先の落ち際に滝を導く） — **残した**。外すと runFlicker は 2,390 に
  下がるが、床の水の行き先に滝の無いフレームが延べ682（163回、中央値3・最長48フレーム）出た。
  床を横へ流れてくる水は量2以上で落ちることがあり、記録（量1だけ）ではつながらない

`tools/render-water-scene.mjs` の水源0・1 を 3000〜3002 フレームで書き出した6枚は、継ぎはぎを外す前後で
画素一致。細い滝は変更前と同じく1本につながって見える。

実装中に計画から変えた点: 水圧の Map 経由のテストの絵（左の池が天井に接していて液面が無く、水圧の
対象にならなかった。上に空気の行を足した）。
