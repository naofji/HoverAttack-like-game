# 水まわりの整理（仕様書に遡ったリファクタリング） 設計書

日付: 2026-09-23
ブランチ: `feat/water-compartment-model`（`4472081` から。9/21 の役割インデックスと
区画モデルの試作は土台にしない — ユーザー判断）

## 目的

4面の水（湖・滝・水源）の処理に、9/6 の仕様書から外れたところ・同じことを
2か所で別々に決めているところ・結果に効いていない処理が積もっている。
仕様書（`2026-09-06-water-cellular-automata-design.md` /
`2026-09-06-water-query-cache-design.md` / `2026-09-06-water-multilayer-rendering-design.md`）
に照らして整理する。

## 進め方（2段）

- **段1 — 挙動を1セルも変えないムダ取り。** `tools/trace-water.mjs` で、実物の Map ＋
  実物の描画を 6シード×2400フレーム（150フレームごとに水辺を爆破）回し、
  水量・種別・液面・アクティブ集合・全セルの問い合わせ結果・描画呼び出しの指紋を
  100フレームごとに取る。変更前後で `--compare` が IDENTICAL であることを各コミットで確かめる。
- **段2 — 矛盾の解消（挙動が変わる）。** 1件ずつ、同じトレースで「何が・どれだけ
  変わったか」を実測してから入れる。採否と実測値はこの文書の末尾に追記する。

## 段1: ムダ取り（挙動不変）

| # | 場所 | 中身 |
|---|---|---|
| 1-1 | `waterSimulation.js` フェーズ2 | `processedSegments` は行ごとに左から右へ1回ずつしか区間を作らないので**一度も当たらない**。区間の列配列 `segCols` と、落ち口の最寄り探索（区間×落ち口の二重ループ）を、左右から1回ずつ走査する形に（同距離なら左、という今の順序を守る） |
| 1-2 | `Map.destroyArea` | 壊れた各ブロックの周囲3×3は `damageBlock` が既にアクティブにしている。同じ Set への再追加なので削る |
| 1-3 | `Map` | `if (!this.activeWaterCells) … = new Set()` の5か所。`_generateWater` が必ず作るので `this.water` があれば存在する |
| 1-4 | `Map.update` / `_sweepDryPockets` | 毎フレーム作り直している `isSolid` のクロージャを `_waterIsSolid` 1本に |
| 1-5 | `environment/water.js` | `map.isSolid ? … : map.grid…` など、テストの偽 map のためだけの迂回路。memory「モック専用のフォールバック分岐はテストが本番経路を通らなくなる」。偽 map 側に本物と同じメソッドを持たせる |

## 段2: 矛盾（候補。1件ずつ実測して採否を決める）

| # | 矛盾 | 案 |
|---|---|---|
| 2-1 | フェーズ2のコメントは「アクティブなセルを含む区間」だが、実際はアクティブな行の**全区間**（マップの端から端まで）を処理している | アクティブなセルを含む区間だけにする。乾いた縦穴の取りこぼし（2-3）との関係を実測 |
| 2-2 | ケースA（落ち口へ流れる）がその場書き換えで左から右へ走査するため、右向きは1フレームで何マスも進み、左向きは1マスしか進まない | 流量を走査前の値から決めてからまとめて適用し、左右対称にする |
| 2-3 | 90フレームごとの全マップ走査 `findStuckDryPockets` は、アクティブ管理の漏れを後から補う応急処置 | 漏れの原因を特定して塞ぎ、走査を撤去できるか実測 |
| 2-4 | 仕様書の「垂直落下 → **斜め滑落** → 水平拡散」の斜め滑落が未実装 | 実装するか、仕様書から外すかを実測で決める |
| 2-5 | `classifyWaterColumn` が「真上が落下中か」を `isFallingCell` と別の条件で判定し直している | 上から走査しているので `kind[k - cols]` を読む |
| 2-6 | `waterSurfaceRow`（しぶき・ドローンの着水）は「上へ水が続く限り」、`getSurfaceY` はキャッシュの液面。水面の定義が2つ。仕様書は配列参照への置き換えを求めていた | キャッシュから導く |
| 2-7 | 描画の `waterTopY` は「paint() と同じ決め方」とあるのに、「沈んでいるか」の判定を持たない。しかも沈み判定を描画側で毎回計算し直している | 1か所で決めて両方が読む |
| 2-8 | 着水の波紋は水源の**列**でしか起こさない。滝が横へずれながら落ちると、着水していない場所で波が立つ | 実際の滝の下端から起こす |
| 2-9 | 水源の停止条件。`Constants.js` は「この行まで水没したら停止」だが、コードが見ているのは水源自身の行で、`r <= 6` の水源は最初から永久に止まっている。もう1つのガードのコメント「必ず岩」は、プレイヤーがその岩を壊せるので誤り | 実際の挙動に合わせて定数とコメントを直す（「止めない」はユーザー判断済み） |

## 結果（2026-09-23）

計測は `tools/measure-water.mjs`（実物の4面 6シード×2400フレーム、150フレームごとに爆破）。
挙動不変の確認は `tools/trace-water.mjs`（水量・種別・液面・アクティブ集合・全セルの
問い合わせ・水の canvas のタイルごとの描画内容・画面の描画、100フレームごと）。

| # | 採否 | 結果 |
|---|---|---|
| 1-1〜1-5 | 採用 | トレース一致。テストの map（`makeWaterMap`）は本物の `Map.prototype` の問い合わせを使う形にした（手で写した `getSurfaceY` / `isWaterAtPixel` が本物と違っていた） |
| 2-1 | 採用（**挙動不変**だった） | 種（前フレームのアクティブ＋このフレームで変化したセルの周り）から区間を広げる形でトレース一致。`map.update()` 中央値 約135µs → 約70µs。前フレームのアクティブだけを見ると、フェーズ1で落ちてきたばかりの水が1フレーム遅れて水量がずれた |
| 2-2 | ケースBだけ採用 | 均しの余りを中央から配る: 左右反転との食い違い 532→358、点滅 −2%。ケースA（落ち口への横流れ）を処理前の水量で決める形にすると食い違いは 288 まで減るが、滝⇄水の点滅が +68% に増えたので見送り（コメントに理由） |
| 2-3 | 採用（撤去） | 拾い直しは一度も何も拾っていなかった。止めても不変条件の違反 0/451万回。トレース一致 |
| 2-4 | 仕様書側を修正 | 斜め滑落は2相モデルに置き換わっていた（CA 設計書に追記） |
| 2-5 | 採用 | 展開すると同値。トレース一致 |
| 2-6 | 採用 | `waterSurfaceRow` を削除。水の状態と描画はトレース一致、問い合わせだけが変化 |
| 2-7 | 採用 | 前景の塗りは一致、岩の背後の水だけが変化（沈んだ浅いセルの隣） |
| 2-8 | 採用 | 12フレームごとの波紋は 旧 1.77個（実際の着水点にあったのは15%）→ 新 1.64個（100%）。**訂正**: コミット `44fc05e` のメッセージの「波紋はもともと判定の約1%」は、`ripples.length` の差で数えた誤り（同じ update の中で古い波紋が消えるぶんと相殺していた）。`addRipple` の呼び出しを数え直した値が上 |
| 2-9 | 採用 | 行6以下の水源は 200シードの 400個中 7個。`WATER_SPRING_STOP_ROW` を削除 |
