# 水まわりの整理（仕様書に遡ったリファクタリング） 設計書

日付: 2026-09-23
ブランチ: `feat/water-compartment-model`（`4472081` から。9/21 の役割インデックスと
区画モデルの試作は土台にしない — ユーザー判断）

## 目的

4面の水（湖・滝・水源）の処理に、9/6 の仕様書から外れたところ・同じことを
2か所で別々に決めているところ・結果に効いていない処理が積もっている。
仕様書（`2026-09-06-water-cellular-automata-design.md` /
`2026-09-06-water-query-cache-design.md` / `2026-09-06-water-multilayer-rendering-design.md`）
に照らして整理する。

## 進め方（2段）

- **段1 — 挙動を1セルも変えないムダ取り。** `tools/trace-water.mjs` で、実物の Map ＋
  実物の描画を 6シード×2400フレーム（150フレームごとに水辺を爆破）回し、
  水量・種別・液面・アクティブ集合・全セルの問い合わせ結果・描画呼び出しの指紋を
  100フレームごとに取る。変更前後で `--compare` が IDENTICAL であることを各コミットで確かめる。
- **段2 — 矛盾の解消（挙動が変わる）。** 1件ずつ、同じトレースで「何が・どれだけ
  変わったか」を実測してから入れる。採否と実測値はこの文書の末尾に追記する。

## 段2: 矛盾（候補。1件ずつ実測して採否を決める）

| # | 矛盾 | 案 |
|---|---|---|
| 2-1 | フェーズ2のコメントは「アクティブなセルを含む区間」だが、実際はアクティブな行の**全区間**（マップの端から端まで）を処理している | アクティブなセルを含む区間だけにする。乾いた縦穴の取りこぼし（2-3）との関係を実測 |
| 2-2 | ケースA（落ち口へ流れる）がその場書き換えで左から右へ走査するため、右向きは1フレームで何マスも進み、左向きは1マスしか進まない | 流量を走査前の値から決めてからまとめて適用し、左右対称にする |
| 2-3 | 90フレームごとの全マップ走査 `findStuckDryPockets` は、アクティブ管理の漏れを後から補う応急処置 | 漏れの原因を特定して塞ぎ、走査を撤去できるか実測 |
| 2-4 | 仕様書の「垂直落下 → **斜め滑落** → 水平拡散」の斜め滑落が未実装 | 実装するか、仕様書から外すかを実測で決める |
| 2-5 | `classifyWaterColumn` が「真上が落下中か」を `isFallingCell` と別の条件で判定し直している | 上から走査しているので `kind[k - cols]` を読む |
| 2-6 | `waterSurfaceRow`（しぶき・ドローンの着水）は「上へ水が続く限り」、`getSurfaceY` はキャッシュの液面。水面の定義が2つ。仕様書は配列参照への置き換えを求めていた | キャッシュから導く |
| 2-7 | 描画の `waterTopY` は「paint() と同じ決め方」とあるのに、「沈んでいるか」の判定を持たない。しかも沈み判定を描画側で毎回計算し直している | 1か所で決めて両方が読む |
| 2-8 | 着水の波紋は水源の**列**でしか起こさない。滝が横へずれながら落ちると、着水していない場所で波が立つ | 実際の滝の下端から起こす |
| 2-9 | 水源の停止条件。`Constants.js` は「この行まで水没したら停止」だが、コードが見ているのは水源自身の行で、`r <= 6` の水源は最初から永久に止まっている。もう1つのガードのコメント「必ず岩」は、プレイヤーがその岩を壊せるので誤り | 実際の挙動に合わせて定数とコメントを直す（「止めない」はユーザー判断済み） |

## 続き: 滝を1本の流れとして描く（2026-09-23 午後）

実機のスクリーンショットで4点の指摘（落ち際・着水点・床を流れる水・滝の横位置）を受け、
さらに2回の追い指摘（湖面の手前で止まる滝／あふれた水が短い四角／水位が上がる途中で
着水点が湖面を横に動く）を受けて決めた描き方。実装は `src/js/world/environment/waterfallRuns.js`
（純関数）と `environment/water.js` の `_drawWaterfalls`。見た目だけで、当たり判定
（`isWaterfallAtPixel`）はタイル単位のまま。

### 前提: セルの中身から見た目を決めてはいけない

- 水源は4フレームに水量1、落下も4フレームに1回なので、滝も床の水も「水量1の塊の列」で、
  **どのセルも周期的に一瞬空になる**
- シミュレーション（ケースA）は床に着いた水を同じフレームで右の落ち口まで運ぶので、
  着水点のセルも床の上のセルも、描く瞬間にはほぼ常に空

そのため見た目は、地形（床・縁・岩の口）と上流（着水点から、シミュレーションが水を運ぶ先の
落ち口まで）から毎フレーム導く。前のフレームの状態は持たない。

### 規則

| 要素 | 決め方 |
|---|---|
| 区間 | 列の中で連続した滝セル。**1セルだけの空きは越えて1本にする**（上端の真上・下端の真下・途中） |
| 上端 | 真上が岩なら「岩の口」: 岩の下面から、`WATERFALL_MOUTH_WIDTH` から帯の幅へ `WATERFALL_MOUTH_TAPER` かけて広がる。横が床の縁（その下が岩か満水）なら「落ち際」: 床を流れる水の上面（縁の向こうが水たまりならその液面）から。どちらでもなければ「空中」 |
| 横位置 | 上端で1回だけ決め、区間の全部で同じ x。岩の口は中央、落ち際は水の来る側の壁から1px。両側が縁なら、実際に水を送ってくる側 |
| 下端 | 床に着くなら床の水の上面、水たまり（床の上の深い水たまりを含む）なら液面。泡の線と跳ねる粒を描く |
| 床の水（着水点から） | 床に着いた点、または**縁まで満ちた水たまり**に着いた点から、`drainColFor`（シミュレーションと同じ: 最寄りの落ち口、等距離なら左）の落ち口まで。厚み `RUNNING_WATER_THICKNESS` |
| 床の水（水たまりの縁から） | 落ち際から水の来る側へ乾いた床を辿り、水たまりに行き着いたら、その縁から落ち際まで（あふれ）。同じ落ち口に着水点からの床の水があればそちらを優先 |
| 床の水の範囲 | **下が岩のタイルの上だけ**、かつキャッシュが既に水を塗っていないタイルだけ（二重塗りのまだら・湖面の上の余計な帯を防ぐ）。流れの筋も同じ範囲だけ |
| 落ち口の滝 | 床の水の行き先の落ち口には、その瞬間セルが空でも滝を描く（下に区間があれば上へ伸ばして1本に） |
| 描かないもの | 湖面の均し: 1セルだけの区間で、すぐ下の段に着水し、両隣の下が湖の水。湖の一番上の段が埋まる途中に現れ、描くと着水点が湖面を横に動いて見えた |

滝は前景のキャッシュに焼かない（区間の遠くのセルが変わるだけで見た目が変わるので、
セル単位で塗り直すキャッシュに向かない）。`drawOverWorld` の中で見えている範囲だけ描く。

### 定数（`Constants.js`）

`WATERFALL_BAND_WIDTH`（8px）、`WATERFALL_MOUTH_TAPER`（8px）、`WATERFALL_MOUTH_WIDTH`（2px）、
`RUNNING_WATER_THICKNESS`（3px）。`WATERFALL_HEAD_DROP` は廃止。

### あわせて直した不具合

- 水源が足した水が `onWaterChanged` を通っておらず、種別キャッシュが「水量1なのに水なし」の
  まま残って、水源の口の滝が数フレームおきに消えていた
- 「沈んでいる」の判定（`isSubmergedFromAbove`）が、岩の上に水が1でもあれば成立していた。
  岩の上面を流れる薄い水だけで岩の真下がタイル全体で塗られ、湖面の上に青い四角が浮いた。
  岩の上の水が半分以上のときだけにした

### 実測

- `drawOverWorld` の時間: 中央値 54→53µs、95% 66→83µs（予算 16.6ms に対して無視できる）
- 区間の見た目の入れ替わり（6シード×600フレーム、3000フレーム後）: 上端 7,813 回（13%）
  → 299 回（0.44%）。1つの落ち際の点いたり消えたり 368→46 回（730 フレーム）

### 確かめ方

- 見た目: `node tools/render-water-scene.mjs --spring 0 --out x.png`（`--frames` で水位の
  上がった後、`--x --y --w --h` で範囲、`--seed` で別の面）
- 点滅: 静止画1枚は良いフレームを写すだけ。`collectWaterfallRuns` の出力を毎フレーム記録し、
  上端・横位置・有無の入れ替わり回数を数える
- テスト: `tests/waterfall-runs.test.js`（指摘ごとに1本。わざと壊して赤くなることを確認済み）
