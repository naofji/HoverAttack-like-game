# 画面比 16:9 対応 — 設計

2026-08-25 / ブランチ `feat/aspect-16-9`

## 目的

内部解像度を 4:3 (1024×768) から 16:9 (1366×768) に置き換える。
**横に広げる**方向で、高さは 768 のまま据え置く。

置き換えであって共存ではない。検証が済んだら main にマージし、4:3 は廃止する。
週次ランキングは全プレイヤー共有（同じ ISO 週＝同じステージ）なので、
移行の前後でスコアの意味が変わらないことを設計の第一条件に置く。

## 解像度を 1366×768 にする理由

高さ 768 を保つ真の 16:9 は幅 1365.33 で整数にならない。1366 は WXGA の実標準
（1366/768 = 1.7786、16:9 の 1.7778 との差は 0.05%）。`style.css` の黒帯計算を
1366:768 の比でそのまま書けば歪みは出ない。

タイル境界（TILE_SIZE=16）の倍数である必要はない。カメラは px 単位の任意位置を
取り、地形描画は `startCol`/`endCol` で切っているため。

以下、この文書では **拡大率 = 1366/1024 = 1.3340** を `ASPECT_SCALE` と呼ぶ。

## 1. 索敵 — 「横だけ画面幅に比例する楕円」

### 問題

索敵はすべてユークリッド距離の**円**で、判定は `dist < sightRange`。
半径は `Constants.js` に `CANVAS_WIDTH * k` の形で集約されている。

| 敵 | k | 4:3 半径 |
|---|---|---|
| タンク | 0.4 | 410 |
| アタッカー standard | 0.4 | 410 |
| アタッカー rival | 0.5 | 512 |
| アタッカー heavy | 0.6 | 614 |
| アタッカー artillery | 0.8 | 819 |
| タレット | 0.5 | 512 |
| ドローン | 0.7 | 717 |
| 基地レーザー | 0.55 | 563 |

HUD 上部 60px を除いたプレイ領域は 4:3 で 1024×708、その半分が 512×354。
円と長方形の組み合わせなので、索敵の公平性は元々アスペクト比の副産物になっている。

`CANVAS_WIDTH` を 1366 に変えるだけだと:

- **横**: 半径も 1.334 倍になるので「半径 ÷ 半幅」は完全に不変。
  タンク 410/512 = 0.80 → 546/683 = 0.80。**横の力関係は 1 ミリも変わらない。**
- **縦**: 半高 354 は変わらないのに半径だけ 1.334 倍になる。
  タンクが真上・真下 546px（現行 410）から撃ってくる。
  **縦の「見えない敵に撃たれる」が一律 33% 悪化する。**

上下移動が主軸のホバー機なので、縦の悪化のほうが体感に効く。

### 決定

索敵を楕円にし、**横だけを画面幅に比例させ、縦は 4:3 時代の絶対値を据え置く**。

```
rx = k * CANVAS_WIDTH        // 横は画面幅に比例
ry = k * SIGHT_VERTICAL_BASE // 縦は 4:3 時代の絶対値（= 1024）

判定: (dx/rx)^2 + (dy/ry)^2 < 1
```

| 解像度 | rx (k=0.4) | ry (k=0.4) | 形 |
|---|---|---|---|
| 1024×768 (4:3) | 410 | 410 | **真円。現行と数学的に完全一致** |
| 1366×768 (16:9) | 546 | 410 | 横にだけ伸びた楕円 |

- 横の比 546/683 = 0.80 ＝ 4:3 と同じ
- 縦の絶対値 410 ＝ 4:3 と同じ

**横も縦も、4:3 のバランスがそのまま保存される。**

### なぜ「ビュー矩形と相似の楕円」にしないか

`rx = k·halfW, ry = k·halfH` という素直な相似案も検討した。「索敵が画面に占める
割合」が完全に不変になる理論的にきれいな解だが、4:3 の時点で
`ry = 0.80 × 354 = 283` となり、**16:9 にする前に縦の索敵が 410→283 に縮む**。
画面比対応にバランス変更が混入するので採らない。

### なぜ半対角基準にしないか

`rx = ry = k × 半対角` は縦の悪化を 1.334→1.236 に緩めるだけで、方向は同じ。
中途半端なので採らない。

### 案A（何もしない）への戻し方

`SIGHT_VERTICAL_BASE` を 1024 から 1366 に変えると ry = rx となり、
「`CANVAS_WIDTH` を変えただけ」＝縦も 1.334 倍の円に戻る。
実機で縦の悪化が気にならなければ、**この定数 1 つで案A に切り替えられる**。

### 実装

`utils/Physics.js` に `withinSight` を新設する。`hasLineOfSight` の隣で、
呼び出し側 5 箇所は既にこのファイルから import しているため。
（`utils/geo.js` は国コードとフラグ絵文字のファイルで、幾何とは無関係。混同しないこと）

```js
/**
 * 楕円の索敵判定。横は画面幅に比例し、縦は 4:3 時代の絶対値に固定されている。
 * 4:3 では rx === ry になり真円に退化するので、移行でバランスは動かない。
 */
export function withinSight(dx, dy, rx, ry) {
    return (dx / rx) ** 2 + (dy / ry) ** 2 < 1;
}
```

半径のペアは `Constants.js` 側で係数から導出して export する。
`ENEMY_ATTACKER_TYPES` の各行は `sightRange: CANVAS_WIDTH * 0.4` を
`sight: 0.4`（係数そのもの）に置き換え、rx/ry は読み出し側で導く。
**表は 1 行 1 係数のまま**にして、CLAUDE.md の「機体ごとの違いは表の 1 行に出る」を崩さない。

差し替える呼び出し箇所:

| ファイル | 現在 |
|---|---|
| `entities/EnemyTank.js:215` | `minDist = ENEMY_TANK_SIGHT_RANGE` の最近接探索 |
| `entities/EnemyTurret.js:257` | `dist < ENEMY_TURRET_SIGHT_RANGE` |
| `entities/EnemyDrone.js:266` | `dist < sightRange` |
| `entities/EnemyAttacker.js:160` | `targetDist <= sightRange` |
| `entities/EnemyBase.js` | `_findTarget(BASE_LASER_RANGE)` 4 箇所。引数を rx/ry のペアにする |

`EnemyTank._findTarget` は「前方 180° の最近接」を選ぶために距離の大小比較を
しているので、単純な真偽値の差し替えでは済まない。楕円の内外は `withinSight` で
判定し、**その中での順位付けは従来どおりユークリッド距離**で行う。
（正規化距離で順位付けすると、横に居る敵が不当に優先される）

### 近接系の絶対定数は円のまま残す

以下は `CANVAS_WIDTH` に紐づいていない小さな絶対値で、画面比とは無関係の
「至近距離の反応」を表している。**円のまま据え置く。**

- `EMERGENCY_DEFENSE_SIGHT_RANGE = 250` — 基地防衛の緊急索敵。
  `EnemyAttacker.js:158` と `EnemyDrone.js:262` で `Math.max(通常索敵, 250)` の形で
  使われている。楕円と混ざるので、**楕円判定と `dist < 250` の OR** に書き換える
  （どちらかに入っていれば発見）。既存テスト 3 本がこの値に依存している
  （`enemy-attacker-emergency-defense` / `enemy-drone-emergency-defense` /
  `base-emergency-defense`）ので、挙動が変わらないことを確認する
- `ENEMY_DRONE_KAMIKAZE_TRIGGER_RANGE = 240` — 体当たり判断。据え置き
- `CARRIER_PROXIMITY_ALERT_RANGE = 80` — 据え置き
- `CRUISE_MISSILE_ACTIVATION_RANGE = 2400` — 桁が違う。据え置き

## 2. 弾の射程 — 索敵を追いかけて伸ばす

### 問題

**発砲のゲートは索敵だけで、別途の射程チェックは存在しない**（`_findTarget` で
索敵に入った標的を返し、そのまま撃つ）。弾は寿命で消える。
射程は `速度 × 寿命` の絶対 px で、`CANVAS_WIDTH` に依存していない。

| | 射程 | 4:3 半幅 512 比 | 16:9 半幅 683 比 |
|---|---|---|---|
| プレイヤー ミサイル (6×180) | 1080 | 2.11 | 1.58 |
| プレイヤー MG (4×180) | 720 | 1.41 | **1.05** |
| 敵 バレット (3×180) | 540 | **1.05** | **0.79** |
| 敵 ホーミング (3×300) | 900 | 1.76 | 1.32 |
| 基地レーザー (`CANVAS_WIDTH×0.55`) | 563 | 1.10 | 1.10（自動追従） |

急所は**敵バレットの 540px**。4:3 ではタレット索敵 512 に対して 5% しか余裕がない
＝手で詰めて調整された値（`PLAYER_MG_LIFETIME` の「80% of original 240」という
コメントも同じ痕跡）。

索敵の rx だけ伸ばすと:

```
タレット  rx 512 → 683   弾 540 のまま  → 143px の「撃たれるが届かない帯」
タンク    rx 410 → 546   弾 540 のまま  → 6px 足りない
```

プレイヤーからは「なぜか当たらない安全地帯」に見える。

### 決定

**弾の寿命を `ASPECT_SCALE` 倍する。**

縦の理不尽は増えない。発砲のゲートが索敵であり、縦の索敵 ry が 410 に
据え置かれている以上、敵は縦 410 の外からは撃ってこないため。
弾が縦に 720 飛べるようになっても、そもそも撃たれない。

| 定数 | 現在 | 新 | 新射程 | カバーすべき rx |
|---|---|---|---|---|
| `ENEMY_BULLET_LIFETIME` | 180 | 240 | 720 | タレット 683 ✓ |
| `PLAYER_MG_LIFETIME` | 180 | 240 | 960 | 半幅比 1.41 を維持 |
| `MISSILE_LIFETIME` | 180 | 240 | 1440 | 半幅比 2.11 を維持 |
| `ENEMY_HOMING_MISSILE_LIFETIME` | 300 | 400 | 1200 | ドローン 956 ✓ |

`ENEMY_BULLET_LIFETIME` は敵 4 種で共有なので、これ 1 つでタンク・タレット・
アタッカーが揃う。180×1.334 = 240.1、300×1.334 = 400.2 で、どちらも切りのいい
整数に落ちる。

### 据え置くもの

- `BASE_LASER_RANGE` — `CANVAS_WIDTH * 0.55` なので自動追従。
  `BASE_LASER_SPEED` は寿命ではなく range 判定なので手当て不要
- `GRENADE_LIFETIME` / `GRENADE_SPEED_MAX_DIST = 200` — 投擲距離ベースで
  画面幅と無関係
- `CRUISE_MISSILE_LIFETIME = 1800` — 30 秒。活性化範囲 2400px と桁が違う

### artillery の射程不足は「元からある仕様」

アタッカー artillery は索敵 k=0.8 で、4:3 の時点で索敵 819 に対し弾 540 と
279px 足りていない。**これは既存の設計**（狙撃型が遠くから発見して寄ってくる）
なので、16:9 でも比を保ったまま残す（rx 1093 / 弾 720）。バグとして直さない。

## テスト方針

### 移行の同一性を証明する（最重要）

`SIGHT_VERTICAL_BASE` の設計上、**4:3 では楕円が真円に退化する**。これを
テストで押さえる:

1. `CANVAS_WIDTH === SIGHT_VERTICAL_BASE` のとき、全敵種で `rx === ry` になる
2. `withinSight(dx, dy, r, r)` が `Math.hypot(dx,dy) < r` と全一致する
   （境界付近を含む格子点で総当たり）
3. 既存の索敵まわりのテストが、係数を 4:3 相当に戻した状態で緑のまま通る

これで「移行でバランスは 1 ドットも動いていない」と言い切れる。

### 16:9 側で新しく縛る

4. 各敵種で `rx / 半幅` が 4:3 の値と一致する（横の力関係の保存）
5. 各敵種で `ry` が 4:3 の絶対値と一致する（縦の力関係の保存）
6. 弾の射程（`速度 × 寿命`）が、対応する索敵 rx 以上ある
   — ただし artillery は既知の例外として除外し、理由をコメントに書く
7. 緊急防衛（250px）の OR 判定が、楕円の外・円の内の点で真を返す

### やらないこと

- **ソース文字列を grep するテストは書かない。** 到達不能でも通ってしまうため
  （CLAUDE.md のテストの流儀）
- 数値の丸め方（240 / 400）はテストで縛らない。実機調整の余地を残す

### 既存テストで期待値が動くもの

`CANVAS_WIDTH` / `LIFETIME` を参照している 20 ファイルを洗う。とくに:

- `tests/audio-panning.test.js` / `tests/audio-falloff.test.js` — `AUDIO_PAN_RANGE`
- `tests/cave-backdrop.test.js` — `camXMax` の算出
- `tests/destruction-finale.test.js` — `SCREEN_DIAGONAL`
- `tests/enemy-*-emergency-defense.test.js` 3 本 — 250px の OR 判定
- `tests/smoke-*.test.js` — 索敵と煙幕の遮蔽

いずれも「`CANVAS_WIDTH` から導く」形に直せば追従するはず。
**ハードコードされた数値があれば、その場で定数由来に直す。**

## 実装の順序

段階ごとに `npm test` が緑になるように割る。

1. `withinSight` を `utils/Physics.js` に足し、真円の場合の同値性テストを書く
   （この時点では誰も使わない）
2. 索敵 5 箇所を `withinSight` に差し替える。**`CANVAS_WIDTH` はまだ 1024 のまま**。
   `SIGHT_VERTICAL_BASE = 1024` なので rx === ry ＝ 挙動は完全に不変。
   既存テストが全部緑のままであることが、差し替えが正しいことの証明になる
3. 緊急防衛 250px の OR 判定を入れる。ここも 4:3 のままなので挙動不変
4. `CANVAS_WIDTH` を 1366 にする。ここで初めて挙動が変わる。
   `style.css` と `index.html` も同時に。既存テストの期待値を洗う
5. 弾の寿命 4 定数を伸ばす
6. 16:9 側の新テスト（4〜7）を足す
7. ユーザーに引き渡して実機確認

**2 と 4 を混ぜないこと。** 混ぜると「楕円化のバグ」と「画面比の影響」が
区別できなくなる。

## 引き渡し時に伝えること

- ハードリロード（Cmd+Shift+R）が要る。`index.html` が `main.js?v=1.0` で
  キャッシュを効かせているため
- 調整用の定数の対応表:
  - 縦の索敵がきつい/緩い → `SIGHT_VERTICAL_BASE`（1024 = 4:3 据え置き、
    1366 = 案A の等方拡大）
  - 敵の弾が届かない → `ENEMY_BULLET_LIFETIME`
  - 自機の弾が届かない → `PLAYER_MG_LIFETIME` / `MISSILE_LIFETIME`
  - 画面が横に広すぎる → `CANVAS_WIDTH`（ただし週次の決定性には無関係）
