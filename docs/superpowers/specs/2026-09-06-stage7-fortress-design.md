# 7面の要塞化 — 段A（地形の形）設計

2026-09-06

## 目的

7面のテーマは「洞窟を改造して作った人工的な要塞」。2026-09-04 の環境設計で
遠景だけ機械にしたが（`backdrop: 'machine'`）、地形そのものは他の面と同じ
洞窟のままで、テーマが遠景でしか読めない。地形の形を人工物にする。

`STAGE_ENVIRONMENTS` の `terrain` 列は、このときのために予約されている
（全行 `'cave'` で、読む側がまだ無い）。今回その読む側を作る。

## 全体は3段に分ける

要塞化は独立した3つの部品からなる。1つの設計書に詰めると大きすぎるので、
段ごとに設計 → 実装 → 実機確認を回す。

| 段 | 中身 | 依存 |
|---|---|---|
| **A（この設計書）** | 地形の形。`terrain: 'fortress'` を読む生成規則 | なし |
| B | 地形の絵。人工物になったタイルを金属パネルで描く | A（どこが人工物かを A が決める） |
| C | 要塞の仕掛け。装甲隔壁・撃つと開く隔壁扉・規則的な砲台の巣・ダメージ床 | A・B（置き場所が要る） |

**段Aだけではタイルの絵は岩のまま**である。人工物に見えるのは装甲（青）と
硬い岩（暗い岩色）の帯、そして室の四隅の柱だけ。実機で見てもらうときは
これを先に伝えること。

C の4要素はユーザーが4つとも入れると決めている。A の生成は「あとで隔壁扉を
置ける場所」（開口）を `fortressZones` に残す必要がある。

## 決めたこと（ユーザーの判断）

| 論点 | 決定 |
|---|---|
| 何を変えるか | 形も見た目も＋要塞らしい仕掛け（＝A・B・C の全部をやる） |
| 人工物の分布 | **区画ごとに混在**。基地に近いほど人工的、ではない。どこに出るか分からない |
| 区画の外壁 | 当初は「正面は壊せない装甲、背面は硬い岩」。**実機を見て作り直した**（節3）。壊せないブロックはやめ、HardMetal 2層で実質難攻不落にする |
| 7面の硬い岩 | **右へ進むほど増やす**（左 0.35 → 右 0.75）。全体も今の一律 0.40 から底上げする |
| 廊下／天井高 | 幅3は窮屈だった。階層構造に変え、天井高5にする（節4） |

## 1. 組み込み方

接ぎ目は1行。

```
Step 9  _placeHardBlocks()                                  硬い岩をばら撒く
Step 9a if (this.envTerrain === 'fortress') this._generateFortress();   ← 足すのはここ
Step 9b 地底湖（4面）
Step 9c 雪の階段（5面）
```

**硬い岩のあとに置く。** 7面は硬い岩の割合が 0.40 あり、要塞区画の中に
4割の確率で硬い岩が混ざると洞窟に戻ってしまう。

要塞は**自分の矩形の中を全部書き潰す**。洞窟生成が掘った空洞も、平滑化が付けた
丸みも、ばら撒かれた硬い岩も、区画の中には残さない（残すと格子が読めない）。
`blockHP` も同時に書く（`BLOCK_NORMAL` は 1、`BLOCK_HARD` は `HARD_BLOCK_HP`、
`BLOCK_INDESTRUCTIBLE` は -1、空洞は 0）。**`grid` だけ書いて `blockHP` を
書き忘れると、硬い岩が1発で壊れる／通常岩が3発耐えるという食い違いが出る。**

- `Constants.js`: `STAGE_ENVIRONMENTS` の7行目を `terrain: 'fortress'` に
- `Map`: `this.envTerrain = STAGE_ENVIRONMENTS[missionLevel % 7].terrain`
  （`envKind` と同じ形）
- 新ファイル `world/fortress.js` の純関数 `carveFortressZones({...})`。
  `waterPools.js` / `snowStairs.js` とまったく同じ引数の形にする
  （`{grid, blockHP, rows, cols, rooms, excludeRects, rng, ...数値}` を受け取り、
  `grid` を加工して結果を返す）

### 乱数

派生ストリーム `new SeededRNG((this.game.rng.state ^ 0xF0A7E5) >>> 0)` を使い、
`game.rng` は1回も消費しない。**これを守らないと週の決定性（同じ週なら同じ敵配置）
が壊れる。** 水と雪が同じ理由で同じことをしている。

**派生ストリームが守っているものの正確な意味**（計画を書く途中で実測して分かった。
誤解しやすいので残す）: 守られるのは「要塞の乱数が洞窟生成の乱数列に割り込まない」
ことであって、「面によらず `game.rng` の総消費回数が同じになる」ことではない。
要塞は `grid` を書き換えるので、あとで走るスポーン探索（`_findEnemyTankPositions`
など）の候補数が変わり、シャッフルで引く回数が変わる。実測すると 6面と7面は
現状ぴったり一致するが（どちらも 150×300 で、間に何も挟まらない）、**5面は雪の
階段が `grid` を変えるせいで 6面より 223 回ずれている**。要塞を入れれば7面も
同じようにずれる。これは正常であり、直すべきものではない。

したがって「7面と6面で消費回数が一致する」形のテストは書けない。書けるのは
「同じ seed なら同じ結果」と「純関数が渡された `rng` だけを使う」の2つ。

### Map が新しく持つデータ

新しいブロック種別は**足さない**。`damageBlock` / 衝突 / ミニマップ / 敵の掩体判定に
波及するのを避けるため、印の配列で持つ（`water` や `exposedAtGen` と同じ方式）。

| 名前 | 型 | 誰が使うか |
|---|---|---|
| `this.fortress` | `Uint8Array(rows*cols)` | **段B**。1 が立っているタイルを金属パネルで描く |
| `this.fortressZones` | `[{r0,r1,c0,c1, openings:[{r,c,side}]}]` | **段C**。隔壁扉・砲台・ダメージ床の置き場所 |

## 2. 区画の選び方

`rooms`（7面で53個）から候補を選び、その中心を中心に矩形を取る。

| 定数 | 値 | 理由 |
|---|---|---|
| `FORTRESS_ZONE_COUNT` | 4 | 150×300 タイルのマップで、通り道に1〜2回当たる密度 |
| `FORTRESS_ZONE_W` | 26〜35 タイル | 画面幅（86タイル）の 1/3。入ったと分かる大きさ |
| `FORTRESS_ZONE_H` | 18〜25 タイル | 画面高（48タイル）の半分弱 |

弾く条件は3つ。`_reservedRects()`（開始の部屋・基地の部屋）と重なる、
マップの縁からはみ出す、既に置いた区画と重なる。水と雪が同じ弾き方を
しているので判定を共有する。

候補が尽きたら、置けた数だけで終わる（`FORTRESS_ZONE_COUNT` は上限であって
下限ではない）。水のプールが同じ扱い。

## 3. 外壁 — 3面は HardMetal、右面だけ HardRock

**2026-09-06 の実機確認で作り直した。** 当初は上・左を `BLOCK_INDESTRUCTIBLE`（壊せない
装甲）にしていたが、実機で「材質が良くない」（＝マップ外周や基地の床と同じ青い磨かれた
絵）という指摘が出た。壊せない装甲はやめ、**HardRock より硬い新ブロック `BLOCK_METAL`
（HP 6）** を作って使う。

厚さは `FORTRESS_WALL_THICKNESS = 2` のまま。

| 帯 | ブロック | 抜けるのに要る弾 |
|---|---|---|
| 上・左・下 | `BLOCK_METAL`（HP 6） | 2層 = **12発**。実質難攻不落 |
| 右（基地側） | `BLOCK_HARD`（HP 3） | 2層 = **6発**。明確な弱点 |

**壊せないブロックを使わずに「実質難攻不落」を作れる**のがユーザーの指摘の要点だった
（厚さ2層あるので 6×2）。副産物として、**要塞がマップを分断する危険が原理的に消える**
（外壁が全部掘れるため）。段Aで作った到達可能性テストはそのまま回帰として残す。

帯の排他的な定義（`zoneBands`）は変えない。角は 左上・右上＝上帯、左下＝左帯、
右下＝下帯に属する。**右帯にだけ `BLOCK_HARD` が来る**ので「弱点は右」がテストできる。

### 被弾の見せ方 — 金属は割れずに焼ける

`BLOCK_HARD` はひび割れで残り HP を見せているが、**金属がひび割れるのは絵として
おかしい**（実機の指摘）。`BLOCK_METAL` は被弾するたびに**熱で赤茶けて艶が飛ぶ**。

- 塗りを `lerpColor(金属色, METAL_HEAT_COLOR, 受けたダメージ / METAL_BLOCK_HP)` で寄せる
- 同時に鏡面ハイライトの強さを落とす（酸化して光沢が飛ぶ）。これが無いと「焼けた」に
  見えず、ただ色が変わっただけになる

描き直しの経路は既存のひび割れと同じ（`invalidateTileRegion` が被弾時に呼ばれる）。

## 4. 区画の中 — 階層構造

**2026-09-06 の実機確認で作り直した。** 当初は縦横同じピッチの廊下の格子にしていたが、
**このゲームは横視点なので、格子は「真上から見た間取り図」に見えてしまう**（実機の指摘）。
建物の断面に見えるよう、横に長い階を縦に積む。

```
■■■■■■■■■■■■■■■■■■■■■■■■   ■ 外壁（上下左=HardMetal, 右=HardRock）
■□□□□□□□▼□□□□□□□□□□□□□□■   □ 空間（天井高5）
■□□□□□□□┃□□□□□□□□□□□□□□■   ▬ 床（HardRock・3発）
■□□□□□□□┃□□□□□□□□□□□□□□■   ↓ シャフト（床の穴）
■□□□□□□□▲□□□□□□□□□□□□□□■   ▼▲ バリアのユニット（天井/床）
■▬▬▬▬↓↓↓↓▬▬▬▬▬▬▬▬▬▬▬▬▬▬■   ┃ 電磁パルスのバリア
■□□□□□□□□□□□□□□□□▼□□□□□■   ◆ お宝
■□□□□□□□□□□□□□□□□┃□□◆◆□■
□□□□□□□□□□□□□□□□□┃□□◆◆□■  ← 左の開口はこの階に開く
■□□□□□□□□□□□□□□□□▲□□□□□■
■▬▬▬▬▬▬▬▬▬▬▬▬↓↓↓↓▬▬▬▬▬▬■
■□□□□□□□□□□□□□□□□□□□□□□■
■■■■■■■■■■■■■■■■■■■■■■■■
```

| 定数 | 値 | 理由 |
|---|---|---|
| `FORTRESS_CEILING_H` | 5 | 天井高（タイル）。自機は 1.5 タイルなのでホバーに余裕がある。幅3の廊下が「若干窮屈」だった実機の指摘を受けた値 |
| `FORTRESS_FLOOR_H` | 1 | 床の厚さ。階のピッチは 5+1=6 |
| `FORTRESS_SHAFT_W` | 4 | 階をつなぐ縦穴の幅 |

区画の高さは 18〜25、外壁2層を除くと内側は 14〜21 行なので **2〜3階**になる。

- **床は `BLOCK_HARD`（3発）。** シャフトを使うのが速いが、掘って階を抜くこともできる。
  掘れないと窮屈になり、掘るのが速いとシャフトの意味が無くなる、その中間
- **シャフトは階ごとに位置をずらす。** 上から下まで一直線に落ちられないようにして、
  各階を横断させる
- **柱と仕切りは置かない。** 当初あった柱は格子の産物で、階層では床が構造を語る。
  進路を塞ぐ役はバリア（節4b）が担う

### 4b. 電磁パルスのバリア（実体は段C。段Aは場所だけ決める）

各階の途中に、**天井のユニットと床のユニットが対**で立ち、その間に縦のバリアが張られる。
横方向の進路を塞ぐので、奥へ行くには**2基とも壊す**必要がある。壁を壊して進むのではなく
装置を倒して進む形にすることで、横視点の遊びとしても成立する。

決めたルール（ユーザーの判断）:

| 論点 | 決定 |
|---|---|
| 触れたとき | **ダメージ＋来た方向へ押し戻される。** 強行突破はできないと体で分かる |
| 弾 | **自機の弾も敵の弾もグレネードも吸収される**（消える）。奥の敵を先に削れない代わりに、奥から一方的に撃たれることもない |
| 敵 | 越えられない。守備隊は奥に籠もり、開けた瞬間に出てくる |
| ユニット | バリアの手前側にあるので、バリアを開ける前でも撫でて壊せる |

**実装済み**（`entities/FortressBarrier.js`）。置き場所は `fortressZones[].barriers`
（`{c, top, bottom}`）で、`SpawnManager.spawnBarriers()` が `game.barriers` に立てる。

実装で決めたこと:

- **敵の一種にはしない。** `game.enemies` に入れると撃破数・スコア・Auto Aim の対象に
  混ざる。地雷と同じく専用の配列に置いて自分で当たり判定を回す
- **2基とも壊すまで消えない**（`active` は OR）。片方で消えると「両方を潰す」という核が
  成立しない。残った1基が張り続けている、という絵として読ませる
- 吸収した弾は `exploded` も立てる。立てないと着弾の爆発と地形破壊が走ってしまう
- 弾の判定は**ユニットを先に見る**。バリアを先に見るとユニットに当てられず開けられない
- ユニットの硬さは砲台と同じ 30（`DAMAGE_PLAYER_MISSILE * 2`）

調整用の定数は `BARRIER_EMITTER_HP` / `BARRIER_TOUCH_DAMAGE` / `BARRIER_KNOCKBACK_*` /
`BARRIER_FIELD_W` / `BARRIER_PULSE_PERIOD` / `BARRIER_COLOR`。

### 4c. お宝と守備隊

- **お宝**: 一番奥の階（開口から最も遠い階の、最も遠い側）に**複数個**。リペアキットと
  オーバードライブキット。オーバードライブは今までアタッカーの撃破ドロップでしか
  出ない稀少品なので、要塞の奥という置き場所が意味を持つ
- **守備隊**: 区画の階に砲台と戦車を追加で湧かせる。実機で「敵がもう少しいてもいい」と
  出た指摘への対応で、7面だけに効く

### 4d. 印

区画の矩形内の「空でないタイル」すべてに `fortress = 1` を立てる。空洞には立てない。

## 5. テスト

新規 `tests/fortress.test.js`。`waterPools` / `snowStairs` のテストと同じ組み立て。
各テストは**わざと壊して赤くなることを確認してから**確定させる。

### 壊してはいけないもの（回帰）

| | |
|---|---|
| 週の決定性 | 生成の前後で `game.rng.state` が一致（1回も消費しない） |
| 他の面 | 1〜6面は `fortress` が全ビット 0、`fortressZones` が空 |
| 再現性 | 同じ seed で同じ区画、違う seed で違う区画 |
| **到達可能性** | **開始の部屋から基地まで、空洞と「掘れるブロック」だけを辿って行ける。装甲は通れない扱いで探索する** |

到達可能性のテストは**今まで存在しない**。要塞は装甲で経路を塞ぎうるので今回作る。
**全7面 × 複数 seed で回す**ので、要塞と関係なく既存のマップが塞がっていないことも
同時に分かる。

### 要塞そのもの

- 区画は `_reservedRects()` と重ならない／互いに重ならない／マップ内に収まる
- 外壁は左辺・上辺が `BLOCK_INDESTRUCTIBLE`、右辺・下辺が `BLOCK_HARD`
- **背面から掘って入れる**（右辺と下辺の帯に装甲が1つも無い）
- 開口は装甲の各辺にちょうど1つ、幅3。開口のマスは空洞
- 区画の中の廊下が全連結（塗りつぶしで数える）
- **掘らずに区画へ出入りできる**（空洞だけを辿る `floodEmpty()` で測る）

**実装して分かったこと（重要）**: 「基地への到達可能性」で開口の効果を縛るつもり
だったが、変異を入れても赤くならなかった。**区画は洞窟の中の島でしかないので、
丸ごと塞いでも経路が迂回して基地には行ける。** 到達可能性テストが言えるのは
「要塞がマップを分断しない」ことだけで、開口が効いているかは測れない
（それ自体は要る性質なので残す）。開口が守っているのは「掘らずに出入りできる」
ことなので、空洞だけを辿るテストで直接測ること。段Cで隔壁扉を入れるときも同じ。
- 印 `fortress` は区画の矩形の中にしか立たない

## 6. 実機での確認

段Aだけでは**タイルの絵はまだ岩のまま**。人工物に見えるのは装甲（青）と硬い岩の帯、
室の四隅の柱だけ。これを承知のうえで見てもらう。

### 実測（実装後。seed 1〜5、7面）

| seed | 区画の数 | 合計面積 | マップに占める割合 | 人工物の印 |
|---|---|---|---|---|
| 1 | 4 | 2418 タイル | 5.4% | 1348 |
| 2 | 4 | 2609 | 5.8% | 1441 |
| 3 | 4 | 2926 | 6.5% | 1577 |
| 4 | 4 | 2718 | 6.0% | 1467 |
| 5 | 4 | 2692 | 6.0% | 1446 |
| **平均** | **4.0** | **2673** | **5.9%** | **1456** |

`FORTRESS_ZONE_COUNT` は上限だが、5 seed とも4個置けている（部屋が53個あるので
候補は十分にある）。区画がマップに占める面積は約6%で、通り道に1〜2回当たる程度。
薄いと感じたら `FORTRESS_ZONE_COUNT` を上げるのが一番効く。

### 実測（第2ラウンド後。seed 1〜5、7面）

| | 実測 |
|---|---|
| 区画 | 5 seed とも 4個 |
| 階 | 区画あたり 2〜3階（4区画の合計で平均 10.6） |
| お宝 | 12個（区画あたり3。うち1個がオーバードライブ） |
| バリアの置き場所 | 平均 10.6本（階の数と一致） |
| 砲台 / 戦車 | 24 / 40（守備隊を足す前は 16 / 32） |

### 見るところ

| 見るところ | 調整用の定数 |
|---|---|
| 区画に入ったと分かるか。4個は多いか少ないか | `FORTRESS_ZONE_COUNT` |
| **建物の断面に見えるか**（真上から見た間取り図に見えないか） | `FORTRESS_CEILING_H` / `FORTRESS_FLOOR_H` |
| 天井高5でホバーが窮屈でないか | `FORTRESS_CEILING_H` |
| シャフトの幅4で降りやすいか。階ごとにずれているのが分かるか | `FORTRESS_SHAFT_W` |
| **金属が岩と見分けられるか。焼けた赤茶が「熱」に見えるか** | `METAL_BLOCK_TINT` / `METAL_HEAT_COLOR` / `METAL_HEAT_GLOSS_LOSS` |
| 12発の正面が「難攻不落」に感じられるか。右が弱点と気づけるか | `METAL_BLOCK_HP` / `FORTRESS_WALL_THICKNESS` |
| 右へ進むほど地形が固くなるのが分かるか | `HARD_BLOCK_CHANCE_BY_STAGE` の7行目 |
| 守備隊の数（区画あたり砲台2・戦車2）が手応えに合うか | `FORTRESS_GARRISON_TURRETS` / `FORTRESS_GARRISON_TANKS` |
| 奥のお宝3個が見つけたときに嬉しいか | `FORTRESS_TREASURE_COUNT` |
| **バリアが「越えられない」と一目で分かるか。2基を壊す遊びが伝わるか** | `BARRIER_FIELD_W` / `BARRIER_COLOR` / `BARRIER_PULSE_PERIOD` |
| ユニット2基（ミサイル4発）が重すぎないか。1本あたりの手間 | `BARRIER_EMITTER_HP` |
| 接触の押し戻しが強すぎ／弱すぎないか | `BARRIER_KNOCKBACK_VX` / `BARRIER_TOUCH_DAMAGE` |

## 7. 段B・段Cへの申し送り

- **段B** は `this.fortress` の印だけを見ればよい。`Map._drawRockyBlock()` の隣に
  `_drawPanelBlock()` を作り、`_drawTile` が印で振り分ける形になる見込み。
  ブロック種別ごとの色（`blockStyles`）とは別の軸なので、装甲・硬い岩・通常岩の
  それぞれに「人工物版」の絵が要る
- **段C** は `this.fortressZones` の `openings` に隔壁扉を立て、室（廊下の交点）に
  砲台とダメージ床を置く。区画の矩形と開口が分かれば置き場所は決まる
